## 2026-01-11 - US-010: Fix overly permissive message UPDATE policy

**What was implemented:**
- Created new migration `20260111200500_fix_messages_update_rls.sql`
- Dropped overly permissive UPDATE policies that allowed any conversation participant to update any message
- Created 3 new restrictive policies:
  1. `Users can update their own messages` - sender_id = auth.uid() for both USING and WITH CHECK
  2. `Studio members can mark received messages as read` - for recipients only (sender_id != auth.uid())
  3. `Client users can mark received messages as read` - for recipients only (sender_id != auth.uid())

**Files changed:**
- `supabase/migrations/20260111200500_fix_messages_update_rls.sql` - New migration

**Security improvement:**
- Before: Any conversation participant could update any message in the conversation (including content of other users' messages)
- After:
  - Senders can only update their own messages (for editing content)
  - Recipients can only update read_at for messages they received (for read receipts)
  - Users cannot modify other users' message content

**Learnings for future iterations:**
- RLS UPDATE policies should use both USING (row access) and WITH CHECK (write validation) clauses
- For sensitive data like messages, separate policies for senders vs recipients provides better security
- All RLS security fixes (US-005 through US-010) are now complete
