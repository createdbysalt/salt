## Codebase Patterns

- **RLS Pattern**: Use studio_id denormalization for efficient RLS. Access via `studio_id IN (SELECT studio_id FROM studio_members WHERE user_id = auth.uid())`
- **Auto-set studio_id**: Use triggers with SECURITY DEFINER to auto-populate studio_id from parent record (e.g., project -> studio_id)
- **Client access**: Client users access data via `project_id IN (SELECT p.id FROM projects p JOIN client_users cu ON cu.client_id = p.client_id WHERE cu.user_id = auth.uid() AND cu.status = 'active')`
- **JSONB defaults**: Use explicit JSONB casting for defaults: `DEFAULT '{...}'::jsonb NOT NULL`
- **Typecheck**: No separate typecheck script. Use `npm run lint` and `npm run build`

  - `idx_seo_audits_studio_id` - list all audits for studio

## 2026-01-10 - US-002: Create Lighthouse API client library

**What was implemented:**
- Created `libs/seo/lighthouse.ts` with `runLighthouseAudit(url: string)` function
- Calls Google PageSpeed Insights API v5 at `https://www.googleapis.com/pagespeedonline/v5/runPagespeed`
- Extracts scores for: performance, accessibility, best-practices, seo (converted from 0-1 to 0-100)
- Returns typed `LighthouseAuditResult` with scores object, full rawData, and fetchedAt timestamp
- Returns `LighthouseError` on failure with descriptive error codes and messages
- Handles specific HTTP errors: 400 (bad request), 429 (rate limited), 500/503 (API unavailable)
- Supports optional `GOOGLE_PAGESPEED_API_KEY` env var for higher rate limits (25k/day vs 400/day)
- Includes `isLighthouseError()` type guard for easy error checking
- Uses mobile-first strategy for audits

**Files changed:**
- `libs/seo/lighthouse.ts` (new)

**Learnings for future iterations:**
- PageSpeed Insights API returns scores as 0-1 decimals, need to multiply by 100
- API supports up to 400 requests/day without key, 25k/day with key
- Mobile strategy is the default best practice for audits
- The `"server-only"` import prevents accidental client-side usage

## 2026-01-11 - US-015: Create CrUX API client library

**What was implemented:**
- Created `libs/seo/crux.ts` with `getCoreWebVitals(domain: string)` function
- Calls Chrome UX Report API at `https://chromeuxreport.googleapis.com/v1/records:queryRecord`
- Extracts Core Web Vitals metrics:
  - LCP (Largest Contentful Paint) - milliseconds
  - INP (Interaction to Next Paint) - milliseconds, replaces deprecated FID
  - CLS (Cumulative Layout Shift) - unitless ratio
- Returns p75 percentile values with threshold status:
  - LCP: good <2500ms, needs-improvement 2500-4000ms, poor >4000ms
  - INP: good <200ms, needs-improvement 200-500ms, poor >500ms
  - CLS: good <0.1, needs-improvement 0.1-0.25, poor >0.25
- Returns `null` (not error) when domain has insufficient traffic data (404 response)
- Requires `CRUX_API_KEY` environment variable
- Includes `isCruxError()` type guard for error checking
- Uses mobile (PHONE) form factor for most relevant real-user data

**Files changed:**
- `libs/seo/crux.ts` (new)

**Learnings for future iterations:**
- CrUX API returns 404 when origin has insufficient traffic - treat as null, not error
- INP replaces FID as the new Core Web Vitals metric for responsiveness
- Mobile (PHONE) form factor provides most representative real-user data
- Domain can be passed as "example.com" or "https://example.com" - normalize to origin format
